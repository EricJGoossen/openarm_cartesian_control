2. Shared design principles

  • No fixed-base branch in core math. Impedance always receives MountMotion; “fixed base” is achieved by external defaults (no IMU) or a future spoof publisher.
  • Separation of concerns. Plain C++ structs (MountMotion, PoseCommandRef) in headers; ROS wiring (subs, RT buffers, params) in the controller plugin.
  • Standard ROS messages only. No custom base-state or pose-command message types.
  • Defaults = old behavior. No IMU → identity orientation, zero velocity. No topic pose yet → hold FK seed from activation. command_source: action → trajectory path unchanged.
  • Incremental dynamics. Full acrobatic ID (Coriolis, free-fall cancellation) is explicitly deferred; API and gravity rotation are in place first.

3. Change set A: moving-base mount motion

3.1 Why

OpenArm was originally written for a fixed bench mount. The user plans to attach the arm to a humanoid bust that can tumble, with IMU and wheel/leg odom on the bust at a known transform to the arm mount. Full humanoid hardware is not available yet, but the controller should be ready to consume real sensor data when it is.

3.2 What changed (files & API)

New file

FileRole
include/openarm_cartesian_control/mount_motion.hpp MountMotion: orientation, linear/angular velocity, linear/angular acceleration, plus has_imu / has_odom flags.

Core impedance (cartesian_impedance.hpp / .cpp)

  • computeControl(...) now takes const MountMotion& mount as third argument.
  • applyMountGravity(mount): mount.orientation.conjugate() * (0, 0, -9.81).
  • computeBiasTorques(q, dq, mount): rotate gravity, then rnea(q, 0, 0) (same as main when orientation is identity).
  • Mount velocity/acceleration fields are accepted but unused — reserved for floating-base inverse dynamics.
// main:
tau += pinocchio::rnea(model, data, q, zero, zero);

// branch:
tau += computeBiasTorques(q, dq, mount);
// internally: rotate gravity from mount.orientation, then rnea(q, 0, 0)

Controller (openarm_cartesian_controller.hpp / .cpp)

  • Subscribes to IMU and odom in on_configure().
  • RealtimeBuffer<MountMotion> for RT-safe handoff to update().
  • imuCallback / odomCallback merge into buffer (non-RT write).
  • readMountMotionFromRT() applies per-sensor defaults when flags are false.
  • Each control cycle: computeControl(q, dq, mount, x_ref_...).

3.3 Sensor → MountMotion mapping

SourceFields writtenNotes
IMU orientation, angular_velocity, linear_acceleration, has_imu=true Vectors rotated by imu_to_mount_rotation_ from param imu_to_mount_rpy
Odom linear_velocity, has_odom=true If IMU not yet received: also uses odom pose orientation and twist.angular
No IMU yet identity orientation, zero ang vel/accel Fixed-base default
No odom yet zero linear velocity Fixed-base default

3.4 Physical picture (future work)

In free-fall, gravity is not “turned off.” Base linear acceleration cancels gravitational effects in the mount frame. IMU linear acceleration is specific force: a_meas ≈ a_base − g. On the ground, IMU reads ~+g upward; in free-fall, ~0. Future computeBiasTorques should use this so feedforward goes to zero when weightless.

4. Change set B: topic vs action pose commands NEW

4.1 Why

The existing FollowCartesianTrajectory action is ideal for test scripts that send a single hold waypoint or a short interpolated move. Production teleop and higher-level planners typically stream target poses at control rate over a topic. Both interfaces should coexist; a config flag picks which is active so tests keep working unchanged.

Mode split:
  • command_source: action — test harness, trajectory interpolation, action feedback
  • command_source: topic — production streaming via geometry_msgs/PoseStamped

4.2 What changed (files & behavior)

New file

FileRole
include/openarm_cartesian_control/pose_command_ref.hpp PoseCommandRef: position, orientation, valid flag. Buffered latest topic command for RT read in update().

Controller changes

  • CommandSource enum: ACTION | TOPIC; parsed from param command_source.
  • RealtimeBuffer<PoseCommandRef> pose_command_buffer_.
  • on_configure(): if topic, create PoseStamped subscription on command_pose_topic (default relative name command_pose → full topic /<controller_ns>/command_pose).
  • poseCommandCallback() (non-RT): writes latest pose; normalizes quaternion; sets valid=true.
  • update() reference selection:
    • Action mode: existing trajectory interpolation (unchanged).
    • Topic mode: if buffer has valid pose, copy to x_ref_pos_ / x_ref_quat_; zero x_ref_linvel_ and x_ref_angvel_ (hold-pose, no reference motion).
  • onGoalRequest(): rejects trajectory goals when command_source == topic with a warning.
  • Unknown command_source string → warn and fall back to action.
  • No stale-topic timeout. Before first message, reference stays at FK seed from on_activate() (same hold-in-place behavior as startup on main).

Config

6. Runtime behavior

6.1 Without any new inputs (matches main)

No IMU/odom → identity orientation, zero velocity → gravity stays (0, 0, -9.81); rnea(q,0,0) unchanged. command_source: action → trajectory tests work as before. Subscriptions are passive — nothing blocks waiting for data.

6.2 With IMU reporting tilt only (change set A)

Gravity direction in the arm model rotates with mount orientation (static tilt compensation). Still no Coriolis, centrifugal, or free-fall effects.

6.3 Topic pose commands (change set B)

With command_source: topic, each new PoseStamped updates the impedance reference immediately. Reference linear/angular velocities are zero — the arm tracks pose with stiffness/damping only (or floats with gravity comp if K/D are zero). Trajectory action goals are rejected.

6.4 Gravity-comp “floaty” feel (unchanged from main)

With k_gains and d_gains all zero, the controller applies only gravity- canceling torques plus any Cartesian clamp logic. There is no spring back to reference and no velocity damping — the arm should feel floaty when pushed; it does not actively maintain last velocity, it simply is not resisted once you stop applying external force.

10. Conversation decisions (do not re-litigate)

  • Rejected custom “base state” ROS message — use IMU + odom directly.
  • Core always takes MountMotion; no separate fixed-base branch inside impedance math.
  • Defaults before sensor data = identity orientation + zero velocity (equivalent to main).
  • Spoof node is external / user-owned for now.
  • Pose commands: keep action path for tests; add topic path for production; default stays action.
  • Pose topic message: geometry_msgs/PoseStamped, not a custom type.
  • Topic mode: zero reference velocities (hold pose), no stale timeout.
  • Do not attempt build unless user asks — env may lack sibling packages.
